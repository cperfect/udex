# Design - ST0026: Open Observability

## Approach

End-to-end OpenTelemetry observability for the Udex server-side (application +
PostgreSQL), with a local Grafana stack for development and the application
coupled only to open standards (OTLP), never to a specific backend. Delivered in
sequenced work packages: runtime stack first, then the telemetry foundation +
server enablement, then deeper instrumentation, the client side, k8s, idempotent
integration tests, and docs.

## Topology (local dev)

```text
                         +------------------------------------------+
 udex server --OTLP/TLS-->  OTel Collector                          |
 udex sdk/cli (traces,     |  - postgresqlreceiver (DB metrics)     |
   spans + metrics + logs) |  - exporters -> Tempo / Prom / Loki    |
                           +---+-----------+-----------+------------+
 udex server --JSON stdout--+  | traces    | metrics   | logs
 postgres/hydra stdout -----+->| Vector ---+-----------+
                               v           v           v
                             Loki        Tempo     Prometheus
                               +--------- Grafana ----------+
```

Signal paths:

- **Traces** - app/sdk/cli -> OTLP (TLS) -> Collector -> Tempo.
- **Metrics** - app -> OTLP (TLS) -> Collector -> Prometheus. PostgreSQL server
  metrics come from the Collector `postgresqlreceiver`. The app adds no second
  listener (stays single-port TLS-gRPC).
- **Logs (hybrid)** - app -> OTLP (TLS) -> Collector -> Loki *when an endpoint is
  configured*; the app *always* also writes JSON to stdout, which Vector (plus
  postgres/hydra container stdout) ships to Loki as the durable floor.

## Design Decisions

### Open-standard boundary

- New `udex-telemetry` crate owns OTel SDK + exporter setup for **binaries**
  (server, CLI): provider construction, OTLP traces/metrics/logs exporters,
  sampling, resource attributes (`service.name`, `service.version`, instance
  id), and graceful shutdown/flush. Check `intent/llm/MODULES.md` + the decision
  tree before creating it; register it there (Highlander).
- The **SDK does not own a provider**. As a library it must not install a global
  tracer/meter provider. It emits `tracing` spans (`#[instrument]`) and injects
  W3C `traceparent` via a client interceptor, composing with whatever OTel
  context the host application already runs. The host (or `udex-telemetry` in the
  CLI) owns the provider.

### Configuration (schema first)

New optional `observability` section on `ServerConfig` (serde/YAML), default
disabled:

```yaml
observability:
  enabled: true            # master switch; default false
  otlp_endpoint: "https://otel-collector:4317"
  otlp_ca: "/etc/udex/otel/ca.crt"   # TLS trust for the Collector
  sample_ratio: 1.0        # 0.0..=1.0 trace head sampling
  traces: true
  metrics: true
  logs: true               # OTLP logs (stdout JSON is always on regardless)
  resource_attributes:
    deployment.environment: "local"
```

- Validated alongside TLS/authz in `ServerConfig::validate()`: ratio range,
  endpoint well-formedness, CA readable when TLS endpoint, per-signal flags.
- When `enabled` is false or `otlp_endpoint` is unset, the app runs with stdout
  JSON logging only and no OTLP exporters (zero overhead, no Collector
  dependency).

### TLS on OTLP

App -> Collector OTLP uses TLS, consistent with the project's TLS-everywhere
principle. Certs are generated by an idempotent script under
`projects/observability/`, folded into `scripts/gen-keys-and-certs.sh`, and
gitignored (same pattern as pod/edge certs). The Collector presents a server
cert; the app trusts it via `otlp_ca`.

### PostgreSQL

- **Server metrics**: Collector `postgresqlreceiver` scrapes the local Postgres
  (per the contrib receiver README) and exports to Prometheus.
- **Client query spans**: sqlx query instrumentation in `udex-datastore`
  produces spans for queries/transactions, correlated with request traces.

### Logs - hybrid

OTLP logs (via `opentelemetry-appender-tracing`) when an endpoint is configured,
plus the existing JSON stdout layer always on. OTLP gives span<->log correlation;
stdout gives crash/Collector-outage durability. Vector ships app stdout +
postgres/hydra container stdout to Loki.

### Metrics - OTLP push

App pushes metrics via OTLP to the Collector, which exposes them to Prometheus.
No second app listener; server stays single-port TLS-gRPC.

### Local dev - opt-in

Observability components layered into the dev stack but off by default (compose
profile + up/down/rebuild script); app telemetry auto-disables when no OTLP
endpoint is configured. K8s dev deployments run with full trace + metric
sampling.

## Architecture

### Runtime stack (`projects/observability/`)

```text
projects/observability/
  docker-compose.observability.yml   # collector, tempo, prometheus, loki,
                                      # grafana, vector
  collector/   config tree (otel collector config, postgresqlreceiver)
  tempo/       config
  prometheus/  config (scrape collector + static)
  loki/        config
  grafana/     provisioning (datasources, dashboards)
  vector/      config (container log -> loki)
  certs/       generated OTLP certs (gitignored)
  scripts/     up.sh / down.sh / rebuild.sh (compose profile layering)
  README.md
```

- **Layering**: observability compose layered onto the base compose via the
  up/down/rebuild scripts (`docker compose -f base -f observability ...`) behind
  a compose `profile`, so a plain `docker compose up` stays postgres+hydra only.
  The devcontainer references it via a symlink (mirroring the existing
  `.devcontainer/docker-compose.yml -> projects/compose/...` pattern); ports
  forwarded as needed (Grafana etc.).
- **Secrets**: Grafana admin credential + OTLP certs generated locally,
  gitignored, surfaced through `.env` / generation scripts. `dev-doctor.sh` gains
  checks for the new artefacts.

### K8s deployment

- OTel Collector runs in-cluster (Deployment; `postgresqlreceiver` points at the
  Compose Postgres via `host.k3d.internal`, matching the existing
  datastore/authz pattern). Tempo/Prometheus/Loki/Grafana remain local-stack for
  dev viewing, or are added to the cluster if needed - decided in WP05.
- App pods get `observability.enabled=true`, the in-cluster OTLP endpoint, OTLP
  CA, and **full** trace + metric sampling (`sample_ratio: 1.0`) via Helm values.

## Alternatives Considered

- **OTLP-only logs (no stdout)** - rejected: loses crash/Collector-outage
  durability; OTLP logs in Rust still effectively need a stdout fallback.
- **stdout+Vector-only logs (no OTLP)** - rejected: trace<->log correlation
  becomes manual string-matching across Loki/Tempo; weaker for the
  performance/reliability tuning goal.
- **Prometheus pull (`/metrics` on the app)** - rejected: would add a second
  listener to a deliberately single-port TLS-gRPC server and split the telemetry
  config surface.
- **Always-on local stack** - rejected: ~6 extra containers in every devcontainer
  by default; opt-in keeps the baseline light while remaining one command away.
- **SDK owning an OTel provider** - rejected: a library installing a global
  provider fights the host app; the SDK stays provider-free and context-aware.
