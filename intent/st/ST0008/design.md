# ST0008: Design — Inject keys and secrets

## Goals

1. No secret material in git — ever.
2. The same injection mechanism works in dev, CI, and prod.
3. Misconfiguration (secret in a config file) is a hard error, not a silent risk.
4. Developer setup is a single command; devcontainer runs it automatically.

## Secret injection pattern

### String secrets → environment variables only

All string secrets are read exclusively from environment variables. They are
never read from a TOML/YAML/JSON config file. The config loader enforces this
at startup.

**Dev:** a gitignored `.env` file at the project root, loaded by the config
system. Generated by `scripts/gen-env.sh`.

**CI:** secrets injected via GitHub Actions secrets / repository variables.

**Prod:** injected via the deployment platform (k8s secrets, ECS task env, etc.).

### Key/cert files → generated, gitignored

Private key and certificate files are generated by `scripts/gen-keys-and-certs.sh`
(which calls the existing per-component regeneration scripts). The generated
paths are gitignored. Config properties that reference these files (`tls.key_path`,
`jwt_public_key_path`) continue to work as-is — file paths are not secrets.

## Config architecture

### Option: adopt the `config` crate

The [`config`](https://crates.io/crates/config) crate provides layered
configuration (defaults → file → environment → overrides) and is idiomatic in
the Rust ecosystem. It would replace the current hand-rolled TOML + struct
approach in the CLI.

**Pros:**
- Environment variable injection is first-class
- Layer ordering is explicit and testable
- Reduces bespoke deserialization code

**Cons:**
- Additional dependency
- Current config structs are simple and well-tested; migration is churn
- The secret-in-file guard is still custom code regardless

**Decision (to be confirmed in WP-03):** Evaluate `config` crate during
implementation. If the migration cost exceeds two days' work, keep the current
loader and implement secret injection as a thin wrapper on top of the existing
`serde`/`toml` stack.

### Secret naming convention

Config struct fields that carry secret values MUST be named with a `_secret`
suffix:

```rust
pub db_password_secret: String,        // good
pub client_secret_secret: String,      // good
pub db_password: String,               // bad — rejected at review
```

The suffix makes secrets grep-able and allows the config loader to enumerate
them programmatically.

### File-injection guard

The config loader parses the raw TOML before deserializing and checks that none
of the keys present match any known `_secret` field names. If a match is found,
startup fails with a clear error:

```text
Configuration error: 'db_password_secret' must not appear in a config file;
inject it via the environment variable UDEX_DB_PASSWORD_SECRET instead.
```

The set of secret field names is derived from the struct definition — no
separate allow/deny list to keep in sync.

### Environment variable mapping

Secret fields map to environment variables with a consistent scheme:

```
{PREFIX}_{FIELD_NAME_UPPER}
e.g.  db_password_secret   →  UDEX_DB_PASSWORD_SECRET
      client_secret_secret  →  UDEX_CLIENT_SECRET_SECRET
```

The `_SECRET` suffix on the env var name makes the intent visible in shell
scripts and CI config.

## CLI — no secrets as arguments

Arguments that currently accept secrets MUST NOT be accepted as positional
arguments or `--flag` values, because those values appear in `ps` output and
shell history. They are read from environment variables only.

Affected CLI args:
- `--token` / `UDEX_TOKEN` — remove flag, keep env var
- `--client-secret` / `UDEX_CLIENT_SECRET` — remove flag, keep env var

If a required secret is absent from the environment, the CLI exits with a clear
error naming the missing variable.

## Developer setup scripts

### `scripts/gen-env.sh`

Generates `.env` at the project root (gitignored). For each secret:
- Generate a fresh random value (e.g. `openssl rand -hex 32`)
- For public/config items (DB host, ports, client IDs), emit the existing
  default or a documented placeholder

Idempotent: prompts before overwriting an existing `.env`, or supports `--force`.

### `scripts/gen-keys-and-certs.sh`

Calls:
- `projects/rust/server/tests/certs/regenerate_certs.sh`
- `projects/rust/server/tests/jwt/regenerate_jwt_signing_key_pair.sh`

Ensures generated output lands in gitignored paths.

### `.devcontainer/post-create.sh`

Runs both scripts unconditionally on container creation so a fresh devcontainer
is fully configured without manual steps. Documented in `docs/setup.md`.
