# Udex Local Dev Environment

Docker Compose configuration for local development and integration testing. Runs **PostgreSQL 16** (the Udex datastore), **Ory Hydra v26.2.0** (the OAuth2 authorization server used for authentication), and the always-on observability fixture.

## Services

| Service | Image | Ports | Purpose |
|---|---|---|---|
| `postgres` | `postgres:16` | `5432` | Udex datastore + Hydra metadata DB |
| `hydra-migrate` | `oryd/hydra:v26.2.0` | — | One-shot migration; runs `migrate sql up` then exits |
| `hydra` | `oryd/hydra:v26.2.0` | `4444`, `4445`, `5555` | OAuth2 server (public, admin, token endpoints) |
| `openobserve` | `public.ecr.aws/zinclabs/openobserve:v0.92.0` | `5080` | Telemetry store, search API and UI |
| `otel-collector` | `opentelemetry-collector-contrib:0.119.0` | `4317`, `4318`, `13133` | OTLP ingest + PostgreSQL metrics; exports to OpenObserve (`13133` is the readiness endpoint) |
| `vector` | `vector:0.44.0-debian` | — | Ships postgres/hydra container logs to the collector |

`hydra-migrate` must complete successfully before `hydra` starts. PostgreSQL must be healthy before either Hydra service starts. See [Observability](#observability) for the last three.

## Prerequisites

Generate the required secrets and environment file before starting:

```bash
# From the workspace root
bash scripts/gen-env.sh
```

This creates `.env` at the workspace root with generated database passwords, Hydra system secrets and the OpenObserve credentials. It is idempotent — re-run with `--force` to rotate. The devcontainer runs this automatically on first create.

## Starting and stopping

```bash
# Start all services (from the workspace root)
docker compose -f projects/compose/docker-compose.yml --env-file .env up -d

# Stop and remove containers (data is lost — see Persistence below)
docker compose -f projects/compose/docker-compose.yml down
```

When using the devcontainer, services start automatically and the above commands are not needed.

## Observability

The observability fixture is **part of this base stack** (ST0027, backend replaced by ST0028) — it comes up with everything else, always-on like PostgreSQL and Hydra (no separate project, no opt-in). It is a three-service OpenTelemetry pipeline:

| Service | Role |
|---|---|
| `otel-collector` (`opentelemetry-collector-contrib`) | OTLP ingest (plaintext gRPC/HTTP) + PostgreSQL server metrics; exports to OpenObserve |
| `openobserve` | Store, query API and UI for traces, metrics and logs — all three in one binary |
| `vector` | Ships postgres/hydra container stdout to the collector (the container-log "floor") |

- **App telemetry is opt-in:** the server/SDK/CLI only emit OTLP when an `observability.otlp_endpoint` is configured (server) or `UDEX_OTLP_ENDPOINT` is set (CLI). The OTLP hop into the collector is **keyless and plaintext** locally — the application stays standard OTLP and can target any backend (see [`projects/rust/telemetry/README.md`](../rust/telemetry/README.md)).
- **OpenObserve UI:** <http://localhost:5080>. Log in with `OPENOBSERVE_ROOT_EMAIL` / `OPENOBSERVE_ROOT_PASSWORD_SECRET` from `.env` (generated by `gen-env.sh`). Nothing needs provisioning — OpenObserve derives its schema from whatever is ingested.
- **Tests** query OpenObserve's search API and treat the fixture as a hard dependency (fail, never skip) like the Hydra tests.

**Nothing upstream of the collector names the backend.** The application emits anonymous OTLP, and Vector sends its container logs to the collector rather than writing to a store directly, so only the collector's exporter config knows where telemetry goes. OpenObserve requires credentials on both ingest and query; that `Authorization` header is terminated in the collector, which is why no application code carries it. (The test helpers, `gen-env.sh`, `dev-doctor.sh` and CI do name the backend, since they query or provision it directly — the agnostic boundary is the *telemetry pipeline*, not the whole repository.)

One consequence of routing Vector through the collector is worth knowing: the container-log floor is no longer independent of the collector. Under ST0027 Vector wrote to the store directly, so container logs survived a collector outage; they no longer do. The server's own JSON-on-stdout floor is unaffected and remains the durable fallback.

The collector and Vector configs are inlined in `docker-compose.yml` (no bind mounts, so they resolve identically in the devcontainer and standalone/CI).

> **Editing compose configs:** `docker compose up -d <service>` does **not** reload a changed inline `configs:` block on a running container — use `docker compose up -d --force-recreate <service>`. Note also that `docker compose start <service>` fails on this stack, because it evaluates `depends_on` differently and objects to OpenObserve having no healthcheck (its image is distroless, so it cannot host one). Use `up -d`.

### Where the data lands

OpenObserve builds its schema from ingested data, so there are no tables to create and none to look up:

| Signal | Where it lands |
|---|---|
| Traces | stream `default` (stream type `traces`) |
| Logs | stream `default` (stream type `logs`) — app telemetry and the container floor together, distinguished by `service_name` |
| Metrics | **one stream per metric**, named after it with dots as underscores (`udex.rpc.requests` → `udex_rpc_requests`) |

Attributes are flattened into columns, dots becoming underscores. One asymmetry is worth knowing before you write a query by hand: in the **traces** stream, resource attributes gain a `service_` prefix (`udex.test.run` → `service_udex_test_run`), while in logs and metrics they do not (`udex_test_run`). Naming a column that does not exist is rejected with `unknown field '...'` rather than returning an empty result, so a mistake is visible rather than silent.

### Charting metrics

Browse at <http://localhost:5080>: [`/web/logs`](http://localhost:5080/web/logs) and [`/web/traces`](http://localhost:5080/web/traces) for search, [`/web/metrics`](http://localhost:5080/web/metrics) to explore a metric, [`/web/dashboards`](http://localhost:5080/web/dashboards) to build panels, and [`/web/streams`](http://localhost:5080/web/streams) to see what has been ingested.

Metrics are queryable with **PromQL**, which is the main practical difference from the previous HyperDX setup — the udex and postgres counters are **cumulative**, so the raw value is a running total and you want `rate()` for per-second figures. Every query below was run against this fixture and returns data:

**Udex services**

| Chart | PromQL |
|---|---|
| Request rate per operation | `sum by (rpc_method) (rate(udex_rpc_requests[5m]))` |
| Errors per operation | `sum by (rpc_method, rpc_grpc_status_code) (rate(udex_rpc_requests[5m]))` — non-zero status is an error |
| p95 latency | `histogram_quantile(0.95, sum by (le) (rate(udex_rpc_duration_bucket[5m])))` |

Histograms are split across several streams on ingest (`udex_rpc_duration_bucket`, `_count`, `_sum`, `_min`, `_max`), which is why the quantile query reads `_bucket`.

**PostgreSQL** (from the collector's `postgresqlreceiver`)

| Chart | PromQL |
|---|---|
| Active backends (connections) | `postgresql_backends` |
| Transaction rate | `rate(postgresql_commits[5m])`, `rate(postgresql_rollbacks[5m])` |
| Disk block reads | `rate(postgresql_blocks_read[5m])` |
| Database size | `postgresql_db_size` |
| Max connections | `postgresql_connection_max` |

Other `postgresql_*` series (bgwriter, index/table stats, rows, operations) follow the same pattern: cumulative counters take `rate()`, gauges are read directly.

## Service URLs

| Endpoint | URL |
|---|---|
| PostgreSQL | `postgres://postgres:<password>@localhost:5432/postgres` |
| Hydra public (token issuance) | `http://localhost:4444` |
| Hydra admin (client management) | `http://localhost:4445` |
| OpenObserve (UI + search API) | `http://localhost:5080` (loopback-only — credentialed, not LAN-exposed) |
| OTLP collector (gRPC / HTTP) | `localhost:4317` / `localhost:4318` |

The full `DATABASE_URL` is written into `.env` by `gen-env.sh` and picked up automatically by `cargo test` and the CLI.

## Hydra setup

Hydra runs in `--dev` mode, which disables HTTPS and consent UI requirements — appropriate for the OAuth2 Client Credentials flow used by Udex. OAuth2 clients (service identities and test fixtures) are registered against the admin API at `http://localhost:4445`.

The helper script `scripts/hydra-create-client.sh` registers a client with the scopes needed for integration tests.

## Persistence

Data is **ephemeral** by default — `docker compose down` wipes both the Udex and Hydra databases. The persistent volume configuration is present but commented out in `docker-compose.yml`. For local testing this is intentional: a clean `up` always starts from a known-good schema.
