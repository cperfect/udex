# Udex Technical Specification

## Overview
Udex is a universal lookup directory for entities designed to be lightweight, fast, and efficient for high-transaction environments, particularly in distributed systems with integration boundaries. It provides entries which are opaque globally unique keys for mapping to contexts, helping to avoid tight coupling and exposure to Hyrum's Law.

## Architecture

### Components
- **Server**: Stateless API layer for processing and routing operations. Built in Rust using `tokio` and `tonic`.
- **CLI**: Developer and operator tool to manage configurations, execute API operations, and perform offline tasks.
- **Datastore**: Abstracted storage backend (initially supporting SQLite and Postgres). All operations are executed transactionally.
- **Configuration**: Static YAML-based config, injected at startup.
- **SDKs**: Code-generated clients in various languages based on gRPC/Protobuf definitions.
- **Telemetry**: OpenTelemetry-compatible metrics and traces.

## Data Model
An index holds a set of entries from Globally Unique Keys to Contexts via the Context's Hash.

### Context
A context is a set of key-value pairs, identified by a hash plus metadata:

#### Rules
- Key-Values pairs are an un-ordered list.
- Keys: Unicode strings, unique within a context.
- Values: Unicode strings, integers, floats, or booleans.
- Max key/value lengths and pair count are configurable per index.
- Byte data must be base64-encoded strings.
- Contexts are immutable.
- Context can optionally include 1 set of envelope encryption data (a Data Encryption Key (DEK) to encrypt the data, and a Key Encryption Key (KEK) Id) that have been used to encrypt one or more of the key value pairs (which will be tagged with the KEK Id).

#### Context Hash
- **Defines identity** of a context within an index.
- Computed by serializing sorted key-value pairs and applying a fast, non-cryptographic hash algorithm (default: SHA-1).
- Configurable hash algorithm per index.
- Metadata is excluded from the hash input.
- The hash is always calculated and provided by the server - it is not possible for the client to set the hash.


### Globally Unique Keys
- Format: UUIDv4 (standard 36-character string)
- Random, non-sortable
- Generated by the server - it is not possible for the client to set the unique key
- Unique across all indices

## Index

### Fields
- `name`: lowercase string, unique, immutable
- `description`: optional, mutable
- `max_bulk_operations`: int ≥ 1
- `max_key_length`, `max_value_length`, `max_kv_pairs_per_context`: configurable limits
- `hash_algorithm`: string (e.g., "sha1", "blake3")

### Metadata
- `created_at`, `created_by`, `updated_by`

## API Design


### Protocols
- Primary: gRPC (using Protobuf v3)
- Optional: REST (via gRPC-Gateway, mirrors gRPC structure exactly)

### Namespaces
- `udex.index.v1`: Index lifecycle management
- `udex.entries.v1`: Entry operations

#### Index Operations
- `Healthz`: healthcheck on index
- `Describe`: info on index

#### Entries Operations (Transactional)
- `CreateEntry`
- `DeleteEntry`
- `LookupContextByKey`
- `LookupKeysByContext`
- `BulkWriteOperation` (ordered, a bulk write represents a single transaction, if one fails they are all rolled back or not applied, mixed-type supported, only write operataions supported)
- `BulkReadOperation` (ordered, mixed type, only read operations supported)

## CLI Tooling

### Features
- Full support for all server APIs (via gRPC)
- Offline utilities:
  - `hash-context`
  - `validate-config`
  - `test-config`
  - `inspect-token`
  - `benchmark`
- Output: table, JSON, YAML
- Built with `clap` using builder pattern

## Configuration
- Format: YAML
- Static (requires restart)
- CLI commands:
  - `udex config validate`
  - `udex config test`

## Security

### Authentication
- OAuth 2.0 Client Credentials Flow
- JWTs validated **locally**
- Supported algorithms:
  - HS256 (HMAC + SHA256)
  - RS256 (RSA + SHA256)
  - ES256 (ECDSA + SHA256)

### Authorization
- Validated before execution
- Bulk operations are rejected if **any** sub-operation fails validation
- Index-level operation permissions
- Configurable bulk operation limits per client
- Admin API permissions TBD

### Encryption
- In transit: TLS 1.3 required for all server and datastore communications
- At rest: Delegated to underlying datastore
- Envelope encryption supported by clients for context values (with metadata)

## Observability

### Logging
- Format: Structured JSON
- Default sink: `stdout`
- Optional: File output

### Tracing & Metrics
- OTLP protocol
- Exposes traces and metrics for:
  - Request handling
  - Datastore interactions
  - Validation steps

### Correlation ID
- Every request assigned a UUIDv4 correlation ID
- Propagated through logs, metrics, and response headers
- Injected by server if not provided by client

## Error Handling

### API Response
```json
{
  "error": {
    "code": "CONTEXT_NOT_FOUND",
    "message": "The requested context was not found in the specified index.",
    "correlation_id": "..."
  }
}
```
- Standard machine-readable codes
- Short, developer-friendly messages (safe to expose)
- Correlation ID always included

### Internal Logs
- Full stack traces
- Detailed diagnostics
- Root cause metadata
- Not exposed in API responses

## Datastore

### Interface Contract
- Opaque to application layer
- Must support transactional bulk ops for entries
- Initial support: Postgres

### Migrations
- Managed via CLI using `refinery`
- Explicit execution (not auto-applied)
- Schema version tracked in DB
